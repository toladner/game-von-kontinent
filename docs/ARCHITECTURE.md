# Aufbau / Architecture

How the system is put together, and — more importantly — where to cut when it
changes.

## The one idea

**A game is a seed plus a list of actions.**

```
GameState_n = fold(applyAction, createGame(seed), [a1, a2, … an])
```

The rules live in a pure reducer with no clock, no DOM and no global state.
Everything else falls out of that:

| You get | Because |
| --- | --- |
| Save / resume | Persist `{seed, names, actions}` — 2 kB, not a state dump |
| Replay & undo | Re-fold a shorter prefix |
| Deterministic tests | Same seed ⇒ same dice, same shuffle |
| Bug reports | The action list *is* the repro |
| Online play later | Ship actions over a wire instead of calling the reducer |
| Bots later | A bot is a function `GameState → GameAction` |

## Layers

Dependencies point strictly downward. Nothing below imports from above.

```
  src/ui/         React components. Presentation only.
  src/app/        Store, wiring, persistence.
        ↓
  src/content/    Data: goods, cards, maps. No logic.
        ↓
  src/engine/     Pure rules. No React, no DOM, no randomness outside rng.ts.
```

`src/engine` has no dependency on `src/content`: it takes a `ContentPack` as
an argument. That is what makes a second map or a second ruleset possible
without touching rules code.

### src/engine

| File | Holds |
| --- | --- |
| `types.ts` | Domain vocabulary + the shape a content pack must satisfy |
| `state.ts` | `GameState`, `PlayerState` — small, serialisable, ids only |
| `actions.ts` | `GameAction` (what players do) and `GameEvent` (what happened) |
| `reducer.ts` | `applyAction(ctx, state, action) → {state, events}` |
| `selectors.ts` | Derived questions: legal moves, sale quotes, standings |
| `context.ts` | Lookup tables built once from a pack |
| `rng.ts` | Seeded, serialisable RNG — the *only* source of randomness |
| `mapbuild.ts` | Ports + legs → the node/lane graph ships sail on |
| `persona.ts` | Procedural traders and quay characters |

### Rule knobs

Every number the Anleitung states is in `RuleConfig`
(`src/content/maps/classic/index.ts`) — starting capital, round count, red
fields, the 75 % loss price, collision damages, the 5-round levy grace period.
Changing balance is editing that object, not hunting through code.

## The three extensions you named

### 1. Time-based travel instead of dice

Movement is already isolated: the reducer only knows `roll` and `step`, and
the ship carries `{nodeId, cameFrom}`. To go real-time:

- Add `etaMs` / `progress` to `ShipState`, and a `tick` action carrying elapsed
  time. `tick` stays deterministic because time arrives *as data*, so replays
  still work.
- Swap `RuleConfig.diceSides` for a `speedKmPerHour`; lanes already know their
  real distance (see `kmPerPip` in `mapbuild.ts`), so an ETA is a division.
- The round track becomes a calendar. `advanceTurn` is the only place that
  knows about turn order — it is ~30 lines.

Nothing in the UI reads dice directly except `AtSeaPanel`.

### 2. Other maps

A map is `ports.ts` + `legs.ts` + `countries.ts`. Ports carry **real lat/lon**,
and `buildMap()` derives the movement pips from great-circle distance, so you
never hand-count dots. To add a world map:

1. New folder under `src/content/maps/`.
2. List ports with coordinates, list which ports connect (`via` waypoints keep
   lanes off the land).
3. Export a `ContentPack`. Register it; the engine and UI need no changes.

`src/content/geo/land.json` is generated by `scripts/build-land.mjs` from
Natural Earth and already contains every continent, not just the four printed
on the original board.

### 3. More resources

Goods are data (`src/content/goods.ts`) and cargo is a list of
`{goodId, pricePaid}`. Adding goods is adding rows. Adding a *new kind* of
resource (coal for fuel, insurance certificates, contracts) means adding a
field to `PlayerState` and an action — the reducer's switch is exhaustive, so
TypeScript will point at every place that must handle it.

Konjunktur cards are already declarative: a card is `{title, lines, effects[]}`
where each effect is a tagged union member. A new effect type is one variant in
`KonjunkturEffect` plus one `case` in `applyEffect`.

### 4. Land routes and bigger vehicles

The graph and the traveller are already separate concepts:

- `Lane.mode` is `'see' | 'land' | 'schiene'`. The classic board only draws sea
  lanes, but the movement code walks edges, not water.
- `Vehicle` carries `{capacity, modes, kmPerPip}` and lives on `PlayerState`.
  The classic steamer is `capacity: null` (the Anleitung sets no limit) and
  `modes: ['see']`.

So "start in a small town with a handcart and trade your way up" needs:

1. Inland nodes and `mode: 'land'` lanes in a map pack.
2. A vehicle catalogue plus a `buyVehicle` action — the reducer already
   enforces `capacity` on every purchase, so a bigger hold immediately means
   more cargo.
3. Filtering `legalSteps` by `player.vehicle.modes`, which is a one-line
   change in `selectors.ts`.

The cargo hold is drawn from `capacity`: give a vehicle a limit and the UI
grows empty crate slots on its own.

### 5. Playing together, across devices and across days

This is the one extension that needs something the browser cannot provide
alone: a place to keep the game while nobody is looking at it.

The design already fits it. A game is `{seed, options, actions[]}` — a couple
of kilobytes. A server does not need the rules at all; it stores the action
list, checks whose turn it is, and broadcasts. Suggested shape:

- **Cloudflare Worker + one Durable Object per game.** The object holds the
  action log and the connected sockets, and survives between visits. Free tier
  covers a game night comfortably, and it deploys next to the static site.
- The client gains a `transport` behind the same `dispatch()` the local game
  uses: local play appends to an array, online play sends the action and waits
  for the echo. Nothing above the store changes.
- **Late joiners** (`joinPolicy: 'jederzeit'`) work because a new player is
  just an action — `joinGame` appended to the log, replayed by everyone.
- **Real-time sailing and asynchronous play are the same feature.** Once a
  ship's position is a function of wall-clock time, "check back this evening"
  is the natural way to play, and the turn order stops being a queue.

## Fidelity notes

Transcribed from the originals in `based/`:

- 72 Warenkarten; buy prices cross-checked against the Warenverzeichnis, which
  is the legible source. Four sell prices carry a `NOTE verify` comment where
  the photographed card is ambiguous.
- 27 Konjunktur cards, exact distribution.
- Red fields read off the board: 5, 9, 13, 16, 21, 26, 29, 34, 39, 43, 48.
- The Warenverzeichnis prints Somalia's *Häute* with card number 66 (Vieh);
  that is a misprint in the original and is corrected to 26.

Deliberate deviations, all reversible in `RuleConfig`:

- The sea-lane graph is reconstructed from real geography rather than traced
  dot-for-dot off the board photo, so pip counts between two ports may differ
  from the printed board by one or two.
- The final round is resolved automatically (sail to the next port in the
  direction of travel, liquidate) rather than played out by hand.
